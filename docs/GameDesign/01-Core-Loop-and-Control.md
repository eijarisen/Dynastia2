# Core Loop and Control

## New Game and calendar
Status: **Implemented**  
Owner: `Dynastia.Mechanics.Family`, `Dynastia.Contracts.GameCalendarConfiguration`

Player-facing purpose: choose when the dynasty begins, create the founding household and enter the yearly simulation.

Rules:
- New Game accepts start years from **1700 through 2000**, snapped to **10-year** increments.
- `2026` is the current technology/content freeze year used by time-aware catalogues.
- A new game creates deceased founding parents, an older bloodline sister and an 18-year-old male-line founder. The exact initial identities and dates are generated from historical name/nationality/location services.
- The founding surname is normalized/generated by the Family plugin. Names and nationalities are year/location aware.

Primary code/data:
- `src/Dynastia.Contracts/GameCalendarConfiguration.cs`
- `plugins/Dynastia.Mechanics.Family/StandardNewGameService.cs`
- `data/Names/`, `data/Nationalities/`, `data/Towns/`

Regression tests: `GameStartYearTests.cs`, `GameCalendarTests.cs`, `TownsNationalitiesBatch3Tests.cs`, `TownsNationalitiesBatch4Tests.cs`.

## Annual action requirement
Status: **Implemented**  
Owner: `dynastia.turn_actions`, application game-flow coordinator

Player-facing purpose: every playable adult male household receives a deliberate annual choice.

Rules:
- Before advancing a year, every currently controllable male-line household head must have a queued annual action.
- `turn.pass` is always available to a valid controller and satisfies the annual-action requirement without another effect.
- The application first reconciles state and lets autonomous households queue their own decisions; it then blocks advancement if a player-controllable heir still lacks an action.
- Only one normal queued action per actor is expected at a time; selection windows/actions may collect parameters before that action is queued.

Primary code:
- `plugins/Dynastia.Mechanics.TurnActions/TurnActionsPlugin.cs`
- `src/Dynastia.App/ViewModels/MainWindowViewModel.GameFlow.cs`
- `src/Dynastia.Core/Actions/ActionRegistry.cs`

## Controller versus selection
Status: **Implemented**  
Owner: `dynastia.succession`, application selection service

Rules:
- **Active Controller** is the person whose household is being directed.
- **Selected Person** is the person currently inspected/targeted in the UI; selecting someone does not automatically transfer control.
- A controller must be alive, male, `lineage.male`, age 18+, locally resident, outside active religious vocation and have a household.
- Changing controller also selects that controller.
- Tab/household cycling changes among controllable male-line household heads.

Primary code:
- `plugins/Dynastia.Mechanics.Succession/StandardSuccessionService.cs`
- `src/Dynastia.App/ViewModels/MainWindowViewModel.Family.cs`
- `src/Dynastia.App/ViewModels/MainWindowViewModel.Selection*.cs`

## Year-resolution pipeline
Status: **Implemented**  
Owner: `Dynastia.Core.Simulation.YearProcessor`

The authoritative phase order is the numeric order of `YearPhase`:

1. `PreYear`
2. `Aging`
3. `QueuedActionsEarly`
4. `Finances`
5. `Status`
6. `Health`
7. `Death`
8. `LifeEvents`
9. `MarriageEvaluation`
10. `MarriageRepair`
11. `MarriageDivorce`
12. `LateMortality`
13. `Inheritance`
14. `Succession`
15. `DerivedState`
16. `PostYear`
17. `MoralsReflection`
18. `FamilyRelations`
19. `FamilyRelationActions`
20. `Thoughts`

Systems inside a phase may declare `Before`/`After` dependencies. The processor validates the complete graph before mutating state, topologically orders systems inside each phase and restores the pre-year checkpoint if a system throws.

Important timing examples:
- early queued treatment/property/community actions can affect later finance/health/life-event phases in the same year;
- economy and loan payments run in `Finances`;
- natural mortality runs after annual Health;
- relationships have separate evaluation/repair/divorce phases after ordinary Life Events;
- inheritance follows late mortality;
- Family Relations actions resolve near the end of the turn;
- Thoughts are generated last.

Primary code: `src/Dynastia.Contracts/YearPhase.cs`, `src/Dynastia.Core/Simulation/YearProcessor.cs`.

Regression tests: `YearProcessorOrderingTests.cs`, `ReliabilityBatchTests.cs`.

## Succession and terminal states
Status: **Implemented**  
Owner: `dynastia.succession`

Rules:
- The dynasty continues while at least one living eligible Male Lineage male remains.
- Active religious vocation removes a male-line person from the succession pool.
- External residence removes local controllability.
- If no living Male Lineage male remains, the dynasty ends as **male-line extinction**.
- If Male Lineage males still live but none remains in Poland/local simulation residence, the terminal state is **dynasty left Poland** rather than extinction.
- Underage Male Lineage boys keep the line alive even though they are not controllable yet.
- When the current controller becomes invalid, the succession service selects the first available controllable person.

Primary code: `plugins/Dynastia.Mechanics.Succession/StandardSuccessionService.cs`, `SuccessionYearSystem.cs`.

## Chronicle, Biography, Thoughts, Genealogy and Map
Status: **Implemented**

- **Chronicle / Family Album** displays structured game events by year.
- **Biography** consumes important events and stores/formats person life-history entries.
- **Thoughts** run after the rest of the yearly simulation and provide current concerns/person emoji context.
- **Genealogy** traverses the bloodline and relationships for family-history inspection.
- **Map** exposes towns, dynasty presence and owned property/local context; town identity is time-aware.

## Save/load expectations
Status: **Implemented**  
Owner: application persistence + plugin/component persistence

Rules:
- Saves are versioned and restore year, start year, people/components/tags, events, selection/controller state, RNG and mechanic state needed for continuation.
- Existing saves keep their stored year rather than being forced to a newer New Game baseline.
- Reconciliation runs on load to restore derived/current invariants and migrate compatible legacy shapes.
- Persistent component/type/field names are compatibility-sensitive. Refactors that rename serialized types or remove fields require deliberate migration.

Primary code: `src/Dynastia.App/Persistence/GameSaveService*.cs`, reconciliation services in Core/plugins.

Regression tests: `NewGameRestartLifecycleTests.cs`, `ReliabilityBatchTests.cs`, migration/reconciliation tests named in the owning mechanic.
